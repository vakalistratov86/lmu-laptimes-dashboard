# CLAUDE.md — LMU Dashboard

## Стек

- Backend: TypeScript (Node.js), парсинг игровых логов (logParser.ts, importWorker.ts)
- БД: хранение sessions, laps, driver metrics
- Frontend: дашборд для визуализации телеметрии (lap-by-lap performance tracking)
- Docker для контейнеризации, Linux/bash окружение разработки

## Правила

- Строгая типизация: TypeScript strict mode, запрет `any` без явного комментария-обоснования
- Все модели данных телеметрии (Session, Lap, DriverMetric) описывать через явные интерфейсы/типы в отдельных файлах моделей
- Парсинг логов — только через чистые функции без побочных эффектов; побочные эффекты (запись в БД, IO) — в отдельном слое (importWorker.ts)
- Ошибки парсинга не должны прерывать импорт всей сессии — логировать и пропускать повреждённую запись
- Все новые поля в схеме БД сопровождать миграцией
- Тесты обязательны для logParser.ts и любых функций трансформации данных

## Запреты

- Не хранить бизнес-логику парсинга внутри React-компонентов дашборда
- Не делать прямых SQL-запросов вне слоя доступа к данным (repository/DAO)
- Не коммитить сырые лог-файлы игры в репозиторий
- Не использовать moment.js — только date-fns или встроенный Intl

## Коммиты

- Формат: Conventional Commits (feat:, fix:, refactor:, chore:)
- Один логический коммит — одна задача
- Обязательное форматирование кода по Prettier перед коммитом (`npm run format`)
- Сообщения коммита и ПР только на русском
- Обновлять всю документацию проекта при каждом коммите, если это требуется

## Ветвление и релизы

`main` — это прод: любой push в `main` автоматически бампает версию
(semantic-release) и деплоит на боевой сервер (`.github/workflows/deploy.yml`).
Прямой push в `main` в обход нижеописанного процесса запрещён.

1. Вся работа — в отдельной feature-ветке от `staging` (не от `main`).
2. PR из feature-ветки открывается **в `staging`**, не в `main`. Мерж —
   обычный merge commit, не squash: `staging` → `main` (следующий шаг)
   должен довезти исходные сообщения коммитов до semantic-release
   нетронутыми, иначе версия/CHANGELOG посчитаются неверно.
3. Мерж в `staging` триггерит `staging-deploy.yml` — автодеплой на тестовый
   стенд (`http://82.202.138.32:3001`, без бампа версии, тег образа
   `:staging`). Ручная проверка — на стенде, не локально.
4. Только после проверки на стенде — отдельный PR `staging` → `main`.
   Только этот мерж уходит в прод.
5. Исключение — критичный хотфикс прод-инцидента: разрешён PR сразу в
   `main` в обход стенда, но обязателен явный `staging` ← `main` сразу
   после (см. п.6), чтобы ветки не разошлись.
6. `staging` обязана периодически подтягивать `main` (после каждого релиза
   или перед началом новой feature-ветки) — иначе новая feature-ветка
   пойдёт от устаревшего `staging` и мерж-конфликт всплывёт поздно.
7. Любое изменение `shared/schema.ts` — в том же PR обязан быть
   соответствующий фиксап в `server/migrate.ts` (создание таблицы/колонки
   или `ALTER ... ADD COLUMN IF NOT EXISTS`/`DO $$...$$` guard для уже
   существующих в проде таблиц). `server/migrate.ts` — единственный
   источник истины по применённой схеме (см. `docs/REQUIREMENTS.md`, §9,
   п.3); без парного фиксапа `shared/schema.ts` и реальная БД расходятся
   молча, и это не поймает ни один тест.
8. Версия в UI на стенде — не `package.json.version` (тот не бампается на
   `staging`), а `X.Y.Z-staging.<short-sha>` (`APP_VERSION_SUFFIX`, см.
   `vite.config.ts`/`Dockerfile`/`staging-deploy.yml`) — не путать с
   настоящим релизом при отладке.
