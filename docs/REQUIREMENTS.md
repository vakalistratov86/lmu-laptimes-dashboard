# Требования к проекту LMU Lap Times Dashboard

> Документ реконструирован из фактического поведения кода (сервер, клиент,
> схема БД, тесты, CI/CD) по состоянию репозитория на момент написания.
> Это спецификация «as-built» — она фиксирует то, что система обязана делать
> сегодня, а не пожелания на будущее. Пункты, отмеченные **[ОГРАНИЧЕНИЕ]**,
> описывают намеренно принятые компромиссы или известный технический долг.

---

## 1. Назначение и область действия

**LMU Lap Times Dashboard** — веб-дашборд для мониторинга и анализа результатов
заездов в симуляторе **Le Mans Ultimate (LMU)** / rFactor2. Приложение
импортирует XML-логи результатов сессий и бинарные `.duckdb`-файлы записи
телеметрии, которые генерирует игра, сохраняет их в PostgreSQL и предоставляет
веб-интерфейс для анализа: лидерборды, историю сессий, профили пилотов, карты
трасс и графики телеметрии.

Приложение **не является** самостоятельным источником данных: оно ничего не
придумывает и не подставляет демонстрационные значения — вся статистика,
кроме статического каталога из 14 трасс, появляется только после импорта
реальных файлов пользователем.

### 1.1 Целевые пользователи

- Игрок/пилот-любитель, ведущий личную статистику заездов в LMU (соло и в
  команде на эндуранс-заездах со сменой пилота).
- Администратор инстанса — единственная роль с повышенными правами,
  аутентифицируется общим `ADMIN_TOKEN` для деструктивных операций.

Многопользовательской модели с индивидуальными аккаунтами, ролями и правами
доступа к данным нет — приложение рассчитано на единственный инстанс с общей
базой данных для одной группы игроков/команды.

## 2. Технологический стек (обязательные требования к среде выполнения)

| Слой | Требование |
|---|---|
| Node.js | ≥ 18 (Docker-образ собирается на `node:20-alpine`) |
| СУБД | PostgreSQL, доступ по `DATABASE_URL` |
| Frontend | React 18, Vite 7, TypeScript 5.6, Tailwind CSS 3, shadcn/ui (Radix), wouter (роутинг), TanStack Query, Recharts |
| Backend | Express 5 (TypeScript, ESM) |
| ORM | drizzle-orm + postgres-js, миграции — `drizzle-kit push` (без versioned-миграций) |
| Телеметрия | `@duckdb/node-api` для чтения `.duckdb` в режиме read-only |
| Валидация | Zod (структурная валидация лога, query/path-параметров REST API) |
| Тесты | Vitest 2 + `@vitest/coverage-v8` |
| Линт/формат | ESLint 9 (flat config) + Prettier, обязательны в CI |
| XML-парсинг | `fast-xml-parser` (полноценное дерево, а не regex) |

Продакшн-контейнер собирается через Docker (`node:20-alpine`), с ручной
установкой `libstdc++`/`libgcc` — обязательное требование, так как нативный
биндинг `@duckdb/node-api` линкуется динамически и падает без них при `require()`.

## 3. Функциональные требования — разделы приложения

Навигация (боковое меню, `client/src/components/AppLayout.tsx`) содержит 7
пунктов в фиксированном порядке: **Overview → Leaderboards → Профиль пилота →
Tracks → Sessions → Telemetry → Events**. Импорт логов и телеметрии доступен
не из бокового меню, а из отдельной иконки в шапке (с пульсирующим
индикатором активности, если фоновый импорт/скан идёт в данный момент —
источник состояния общий для страниц Import и Telemetry Import).

### 3.1 Overview (`/`)

1. Отображает 8 KPI-плиток в фиксированном порядке (2 строки): пройдено
   расстояния, число трасс, число пилотов, лучший круг, число гонок,
   реальных игроков, ИИ-игроков, кругов пройдено.
2. Ниже — график лучшего времени круга по трассам.
3. Классификация «Гонка» вычисляется через единый нормализатор
   `normalizeSessionCategory()` (см. §3.11) — точное сравнение строк
   недопустимо, т.к. реальное значение бэкенда — составная строка
   (`«Гонка (Race1)»`).
4. При пустой БД раздел показывает пустое состояние с призывом перейти
   к импорту, а не нулевые/фиктивные значения.

### 3.2 Sessions (`/sessions`)

1. Сводная плитка сверху показывает количество и суммарное время отдельно
   для тренировок / квалификаций / гонок, оформленные в цветах
   соответствующего фильтра.
   - Суммарное время «Гонка» считается из `race_time_min` (не
     `session_duration_min`, который заполняется только для практики/квалификации).
   - На экранах уже `sm` текстовые подписи плиток скрыты (остаётся иконка +
     значение), но остаются доступны скринридерам через `sr-only`.
2. Сегментированный переключатель фильтра по типу сессии: `Все` /
   `Тренировка` / `Квалификация` / `Гонка`. Активный фильтр обязан
   сохраняться в query-параметре URL, чтобы кнопка «Назад» из деталей
   сессии возвращала пользователя в тот же отфильтрованный список.
   На мобильном фильтр обязан быть горизонтально прокручиваемым, а не
   обрезать последнюю секцию.
3. Таблица сессий — колонки: тип сессии, **тип гонки** (бейдж «Соло»/«Команда»
   по `sessions.has_co_drivers`, сразу после колонки типа сессии), трек,
   классы машин (участвовавшие в сессии), лучший круг, число кругов, дата.
4. Строки таблицы полностью кликабельны (hover, `cursor:pointer`, доступны
   с клавиатуры) и ведут на `/sessions/:id`.
5. На мобильном таблица обязана скроллиться по горизонтали
   (`overflow-x-auto`), а не обрезать недоступные для просмотра колонки.

### 3.3 Session Detail (`/sessions/:id`)

1. Верхний блок — статичная плитка **`SessionInfoCard`** с информацией только
   о трассе и сессии (тип, трек, конфигурация, дата), не зависящая от
   активной вкладки и от выбора пилота.
2. Карточка **`SessionDriverDetailCard`** — всегда видима (не сворачивается),
   по умолчанию показывает позицию №1. Содержит: результат, класс, команда,
   лучший/средний/худший круг, отставание, интервал, пит-стопы, макс.
   скорость, топливо, состояние шин, все три сектора, теоретически лучший круг.
3. Вкладки **Результаты / Круги / Прогресс** встроены прямо в шапку карточки
   результатов (не отдельный блок над ней).
4. Раскраска секторов и медалей:
   - Зелёный — личный лучший сектор пилота за сессию.
   - Фиолетовый — абсолютный лучший сектор среди всех участников сессии
     (приоритетнее зелёного).
   - Медали 1/2/3 места окрашены по-разному (`getMedalColorClass()`), не
     одним и тем же цветом.
5. Клик по строке в таблице результатов выбирает пилота — карточка деталей
   и вкладка «Круги» переключаются на него.
6. **Командная гонка со сменой пилота** (`has_co_drivers = 1`):
   - Таблица «Результаты» группируется по машине (не по пилоту), с
     суммарной статистикой команды: Σ кругов, Σ пит-стопов, минимальный
     лучший круг среди пилотов машины.
   - Карточка деталей показывает только лучший результат команды в целом.
   - Вкладка «Круги» показывает дополнительный столбец «Пилот» — кто вёл
     машину на каждом конкретном круге. Столбец показывается только когда
     у машины реально больше одного пилота за сессию.
   - Вкладка «Прогресс» рисует одну линию на машину (не по перекрывающимся
     отрезкам на каждого со-пилота).
7. Порядок колонок таблицы «Результаты»: Поз. → Пилот → Команда → Класс →
   Авто → Статус → Кругов → Пит → Лучший круг → Отставание.
8. Loading/empty/no-results состояния обязательны для: сессия не найдена
   (404), нет данных по кругам, нет данных для графика.

### 3.4 Leaderboards (`/leaderboards`)

1. Вертикальный список полноширинных карточек, сгруппированных по
   `trackName + course` (одна физическая конфигурация трассы = одна карточка,
   даже если разные сессии называют её слегка по-разному в логе).
2. Внутри карточки — разбивка рекордов по классам машин, с медалями,
   отставаниями от лидера, датой и временем установки рекорда (без
   бессмысленного «12:00 AM» — данные хранятся без времени, только дата).
3. Фильтр по конфигурации трассы (`course`).
4. На узких экранах колонки «Команда»/«Автомобиль»/«Дата» скрыты, остальные
   обрезаны по `max-width` с `truncate`, чтобы время круга/отставание не
   выталкивалось за пределы экрана.

### 3.5 Tracks (`/tracks`) и Track Detail

1. Каталог трасс с амбер-подсветкой контура на схематичной карте.
2. Блок рекордов, блок «Интересно» (факты о трассе), рейтинг по трассе.
3. При пустой БД в таблицу `tracks` **гарантированно** подставляется каталог
   из 14 известных трасс LMU при каждом старте сервера — единственное
   исключение из правила «нет данных без импорта» (см. §3.13) — но их
   статистика (рекорды/сессии/круги) остаётся нулевой до первого импорта.
4. На мобильном: у значения рекорда круга обязательны `min-w-0`/`truncate`
   (иначе длинное время круга наезжает на соседнюю ячейку); схема трассы
   сужена с 144px до 96px на мобильных экранах.

### 3.6 Профиль пилота (`/profile`, `/drivers/:id`)

1. `/profile` — страница-пикер: `DriverFilterBar` в режиме `single`
   (выбор ровно одного пилота), под ней — содержимое профиля.
2. `/drivers/:id` — прямой переход на профиль конкретного пилота (например,
   из таблицы результатов сессии), с кнопкой «Назад» на Leaderboards.
3. Оба маршрута рендерят общий компонент `DriverProfile`, содержащий:
   - Шапку: имя (с иконкой игрок/ИИ), команда, страна, бейдж «Игрок c
     года X» (год первого появления пилота в данных).
   - KPI-плитки: лучший круг (+трасса), число сессий, число кругов
     (+любимая трасса по числу кругов), победы, подиумы, средняя позиция.
   - Таблицу личных рекордов по трассам: трасса+конфигурация+класс,
     личный лучший круг, отставание от абсолютного рекорда трассы (или
     бейдж «Рекорд трассы», если пилот сам его держит), дата.
     Ключ группировки обязан включать `course` — трасса с несколькими
     конфигурациями layout под одним `trackId` не должна схлопывать разные
     конфигурации в одну строку личного рекорда.
   - Историю сессий пилота (клик — переход в `/sessions/:id`), с пометкой
     диапазона стинта (`stintStartLap`–`stintEndLap`), если пилот участвовал
     в командной гонке со сменой пилота не с начала до конца сессии.
   - Таблицы инцидентов и нарушений трек-лимитов — **только по гоночным
     сессиям** (не по практике/квалификации), с ролью пилота в инциденте
     («виновник» / «пострадавший») и вторым участником.
4. «Любимая трасса» и группировка рекордов ведутся по `trackId`, а не по
   имени трассы — разные физические конфигурации с одинаковым названием
   (напр. Bahrain GP и Bahrain Outer Circuit) не должны схлопываться.

### 3.7 Telemetry (`/telemetry`) и Telemetry Detail

1. Список импортированных записей телеметрии: пилот, трасса, дата/время заезда.
2. Detail-страница:
   - Карта трассы по GPS-треку выбранного круга.
     - Для откалиброванных трасс (на данный момент — только
       Spa-Francorchamps) — поверх реального спутникового снимка (мозаика
       тайлов Esri World Imagery), с зумом (колесо/кнопки, потолок 24×) и
       паном.
     - Для остальных трасс — схематичный SVG-фолбэк (`telemetryGeo.ts`).
     - Траектория круга раскрашена по скорости в каждой точке
       (зелёный → жёлтый → красный, от медленного к быстрому).
     - У каждого поворота — подписи максимальной скорости перед поворотом
       и минимальной скорости в апексе; близкие метки (< 40 м по дистанции
       круга) дедуплицируются, остаётся более выраженная.
     - Курсор — треугольная стрелка по направлению движения; линия
       старт/финиш поперёк полотна трассы; направление обоих элементов
       считается по широкому окну соседних GPS-точек (не по одному соседу),
       чтобы убрать шум.
   - График каналов телеметрии (скорость, педали и др.) с выбором круга
     из списка и синхронизированным зумом/легендой.
   - Круги нумеруются с 1 (не с 0/аутлапа), время круга форматируется тем
     же общим форматтером, что и на вкладке «Сессия» (не собственным
     `toFixed(1) + "s"`).

### 3.8 Import (`/import`)

1. Две вкладки: **логи** и **телеметрия**, с независимыми панелями/журналами.
2. **Логи**:
   - Выбор папки через File System Access API (с fallback обычного выбора
     файлов/папки для браузеров без поддержки — предупреждение об этом
     показывается явно).
   - Каждый файл отправляется отдельным запросом `POST /api/import`.
   - Автоимпорт: периодическое повторное сканирование выбранной папки по
     таймеру (интервал — константа `AUTO_INTERVAL_MS`), включается тумблером.
   - Журнал импорта (построчно, с иконкой+цветом по уровню: `ok` зелёный,
     `error` красный, `skip` жёлтый, `warn` амбер, `info` нейтральный) и
     список уже обработанных файлов — персистентны в localStorage/IndexedDB,
     переживают перезагрузку страницы.
   - Счётчики: обнаружено / в очереди / импортировано / пропущено / ошибок.
   - Движок импорта (папка, журнал, счётчики, авто-скан, сам цикл) обязан
     жить в провайдере уровня приложения (`logImportEngine.tsx`), смонтированном
     выше роутера — переход на другую вкладку приложения не должен прерывать
     фоновую загрузку.
   - Кнопка полной очистки БД с предупреждением о необратимости — требует
     admin-токен (см. §6.5).
3. **Телеметрия**: загрузка `.duckdb`-файла (до 150 МБ) — `POST
   /api/import/telemetry`, отдельный журнал/счётчики, отдельная кнопка
   очистки телеметрии (не затрагивает данные заездов).

### 3.9 Events (`/events`)

1. Две вкладки: **Daily Races** и **Special Events**.
2. Даты форматируются как `DD.MM.YYYY`.
3. Данные Special Events парсятся с внешнего источника (lemansultimate.com)
   с кэшем и фолбэком на статические данные при недоступности источника
   или изменении вёрстки страницы (см. §5.7). **[ОГРАНИЧЕНИЕ]** LMU не
   предоставляет публичного API для Daily Races — ротация добавлена статически
   в коде (`DAILY_RACES_STATIC`), требует ручного обновления при смене сезона.

### 3.10 Общие UI-требования

1. Единая иконка пилота (`DriverName`): зелёный человечек — реальный игрок,
   жёлтый робот — ИИ. Используется везде, где отображается имя пилота
   (Sessions, Session Detail, Leaderboards, Tracks, `DriverFilterBar`,
   профиль пилота) — не текстовый бейдж «AI».
2. `DriverFilterBar` — searchable multi-select с секциями «Выбрано / Игроки /
   ИИ», переключателем «Показать ИИ» и «Выбрать все» (массовый выбор всего
   видимого списка). Поддерживает режим `single` (ровно один выбранный
   пилот, используется профилем пилота) и обычный multi-select.
3. Тематизированный скроллбар (тонкий, в цвет текущей темы) во всём
   приложении вместо системного — работает и на WebKit, и на Firefox,
   в обеих темах.
4. Светлая и тёмная темы, переключатель в шапке; выбор темы не сбрасывается
   при навигации.
5. Мультиязычность: переключатель RU/EN в шапке. Определение языка по
   умолчанию — сохранённый выбор в `localStorage`, иначе язык браузера.
   Переводы — плоские dot-path ключи (`t("namespace.key")`) с подстановкой
   переменных и склонением числительных для русского языка (`tn()`).
   TypeScript обязан проверять соответствие ключей между `ru`/`en` словарями
   на этапе компиляции. Даты/время форматируются через `Intl` с учётом
   текущей локали (включая русские родительные падежи месяцев), а не
   захардкоженными массивами.
6. Адаптивная вёрстка: на мобильном — выпадающее меню навигации вместо
   бокового сайдбара; ключевые таблицы прокручиваются горизонтально, а не
   теряют данные при сужении экрана (проверено на 390px).
7. Единый источник стилей/цветов для типов сессии, классов машин и медалей —
   `client/src/lib/classStyles.ts` (`normalizeSessionCategory`,
   `SESSION_TYPE_BADGE`, `getMedalColorClass`, `getClassBadgeClass`).
   Дублирующие локальные реализации в отдельных страницах недопустимы.
8. Единый источник форматирования времени круга/сектора — `client/src/lib/
   format.ts` (`formatLap`, `formatSector`, `formatDelta`) — должен сам
   проверять невалидные значения (`NaN`/`Infinity`/`<=0`) и рисовать «—»,
   а не полагаться на каждое место вызова.

### 3.11 Нормализация типа сессии

Единая функция `normalizeSessionCategory()` сводит любые варианты типа
сессии из лога (`Practice1..4`, `Warmup`, `TestDay`, `Qualify1/2`, `Race1/2`
и человекочитаемые префиксы `«Практика»/«Прогрев»/«Тесты»/«Квалификация»/
«Гонка»`) ровно к трём категориям: **тренировка / квалификация / гонка** —
через подстроковое сравнение, а не точное совпадение строк (реальный формат
бэкенда — составные строки вида `«Гонка (Race1)»`). Все места приложения,
считающие/красящие/фильтрующие по типу сессии, обязаны использовать эту
функцию — независимые реализации приводят к рассинхрону (задокументированный
класс багов, см. CHANGELOG).

### 3.12 Отсутствие фейковых данных

Приложение не подставляет демонстрационные/заглушечные данные. При пустой
БД разделы Overview / Leaderboards / Tracks / Sessions / Session Detail
обязаны показывать пустое состояние с явным призывом импортировать логи —
никаких «нулевых» или синтетических записей. Единственное исключение —
статический каталог 14 трасс в таблице `tracks` (см. §3.5, п.3).

## 4. Требования к обработке XML-логов (сервер)

### 4.1 Формат входных данных

Источник — `<rFactorXML><RaceResults>...</RaceResults></rFactorXML>`,
генерируемый rFactor2/LMU. Парсинг обязан использовать полноценное дерево
XML (`fast-xml-parser`), а не построчный regex — регексовый подход не
переживал CDATA, экранированные спецсимволы и вложенные одноимённые теги
в разных ветках.

1. Версия формата детектируется до парсинга (`detectLogVersion`) и
   валидируется (`assertSupportedVersion`) — неподдерживаемая версия обязана
   провалить импорт с понятным сообщением, а не тихо потерять данные.
2. Тип сессии определяется по имени тега-обёртки внутри `RaceResults`
   (`TestDay`, `Practice1..4`, `Warmup`, `Qualify1/2`, `Race1/2`), с фолбэком
   на всю секцию `RaceResults`, если ни один известный тег не найден.
3. `Minutes`/`Laps`/`MostLapsCompleted` обязаны читаться **изнутри** тега
   конкретной сессии (например, `<Practice1><Minutes>`), а не с корня
   `RaceResults` — это единственное место, где эти теги реально
   встречаются в практике/квалификации (баг, ранее дававший всегда `null`,
   исправлен и покрыт тестом).
4. `TrackEvent` — обязателен как основной идентификатор события; пустой
   (но присутствующий) тег обязан фолбэчиться на `TrackVenue`, а не
   оставаться пустой строкой.
5. Дата сессии: приоритет — Unix-время из тега `DateTime` (секунды),
   фолбэк — `TimeString` (`"YYYY/MM/DD HH:mm:ss"`), иначе — текущее время.
6. Круги (`<Lap num=... s1=... s2=... s3=... pit=... topspeed=... fuel=...
   twfl=... FL=... />`) читаются вместе со всей телеметрией круга: топ-спид,
   уровень и расход топлива, состояние 4 шин, состав шин перед/зад.
   Незачтённые круги (`"--.----"` и т.п.) обязаны парситься как `null`, не
   как `0` или ошибка.
7. Stream-секция (`<Stream>`, может лежать как прямым потомком
   `RaceResults`, так и внутри секции конкретной сессии — искать
   рекурсивно): инциденты (`<Incident>`), лучшие времена секторов
   (`<Sector>`), нарушения трек-лимитов (`<TrackLimits>`), смены пилота
   (`<DriverChange>`).
   - Данные `Incident`/`Sector`/`TrackLimits` в реальных логах лежат в
     **атрибутах** тега и человекочитаемом тексте, а не во вложенных тегах
     с именами полей — парсер обязан разбирать текстовый шаблон
     (`"Имя(N) reported contact (severity) with ..."` и т.п.) через
     задокументированные регэкспы, а не предполагать структуру по названиям.
   - Записи с нераспознанным текстовым форматом (не совпавшие с regex)
     обязаны отбрасываться молча (не порождать запись с фиктивными данными),
     а не валить импорт целиком.
   - `<Sector>`-тег переиспользуется игрой и для не относящихся к сектору
     событий (например, сообщений о повреждении подвески) — записи без
     атрибута `Driver` обязаны игнорироваться.

### 4.2 Командные гонки со сменой пилота (`<Swap>`/`<DriverChange>`)

1. `<Swap startLap="N" endLap="M">Имя</Swap>` внутри блока `<Driver>` — список
   стинтов машины. Если тегов нет (обычный сольный заезд), парсер обязан
   синтезировать **ровно один** стинт на весь диапазон кругов машины —
   downstream-код не должен знать отдельной ветки «без свопа».
2. `<DriverChange et="...">Slot=N Vehicle="..." Old="Имя1" New="Имя2"
   </DriverChange>` из Stream даёт точное время смены пилота в секундах;
   сопоставляется с границами стинтов по именам (Old/New), не по Slot.
3. Сессия помечается `has_co_drivers = 1`, если **хотя бы у одной** машины
   различаются имена в разных стинтах.
4. `driver_count` сессии обязан считать различных **реальных пилотов**
   (по стинтам), а не количество блоков `<Driver>` (машин) — иначе
   со-пилот, не оказавшийся последним за рулём, не попадает в счётчик.
5. На каждого реального пилота машины создаётся **отдельная** строка
   `session_results`. Поля машины (`team`/`carNumber`/`vehName`/`category`/
   `position`/`classPosition`/`finishStatus`) одинаковы у всех строк одной
   машины; `laps`/`pitstops`/`bestLapMs` обязаны быть пересчитаны **по
   факту** из собственных кругов этого пилота — машинным `<Laps>`/
   `<Pitstops>`/`<BestLapTime>` из XML доверять нельзя: это агрегаты по
   машине целиком, включающие круги со-пилота (подтверждено на реальном
   логе: чужой лучший круг записывался как личный рекорд другого человека).
6. `session_results.stintStartLap`/`stintEndLap`/`stintStartSec`/`stintEndSec`
   — диапазон стинта пилота; `null` для сольной машины (не участвовавшей в
   свопе). При появлении одного и того же пилота в 2+ несмежных стинтах
   (свап туда-обратно) диапазон — `min(startLap)`/`max(endLap)` по всем
   стинтам (лоссовое сжатие, не список интервалов).
7. `isPlayer` для машины со сменой пилота обязан проставляться `1` **всем**
   реальным со-пилотам — участие в `<Swap>` само по себе является
   доказательством реального человека (ИИ не «сменяют» по имени в логах
   игры). Машинный `<isPlayer>` (единственный флаг на всю машину, относится
   только к «зачётному» пилоту) недостаточен и не должен использоваться
   напрямую для со-пилотов.
8. `session_laps`/`lap_times` каждого круга обязаны резолвиться по
   `driverId` того стинта, в диапазон которого попадает `lapNum` (не
   привязываться к одному «зачётному» пилоту машины на всю сессию).
9. Stream-события (инциденты/секторы/трек-лимиты), ссылающиеся на реального
   пилота, не зарегистрированного среди участников сессии, обязаны
   попадать в DLQ (`import_errors`, `SEMANTIC_ERROR`) с логированием, а не
   молча теряться — актуально в первую очередь для со-пилотов.

### 4.3 Нормализация (`server/normalizer.ts`)

1. Названия трасс приводятся к каноничным через таблицу алиасов
   (`TRACK_ALIASES`) — разные написания одной трассы в разных логах не
   должны порождать разные строки в `tracks`.
2. Имена пилотов — `trim` + схлопывание повторяющихся пробелов для
   хранения; отдельно — `trim` + `lowercase` для сравнения/поиска
   (регистронезависимое сопоставление одного и того же человека).
3. Единицы времени круга детектируются эвристикой и приводятся к целым
   миллисекундам: значения < 3600 с дробной частью или целые < 1000
   трактуются как секунды и домножаются на 1000, иначе значение уже
   считается миллисекундами.
4. Дата/время приводится к UTC ISO-строке; невалидная дата обязана бросать
   ошибку явно, а не молча фолбэчиться на текущее время.

### 4.4 Сопоставление трассы с БД (`findOrCreateTrack`)

1. Поиск существующей трассы сперва идёт по каноничному названию (без
   полного сканирования таблицы), затем:
   - точное совпадение layout/course, либо
   - совпадение по длине трассы в пределах допуска 0.05 км (одна и та же
     физическая конфигурация может приходить под разными строками `course`
     в разных логах, при этом `trackLengthM` совпадает или почти совпадает).
2. Разные реальные конфигурации одной трассы с разной длиной (например,
   Bahrain GP 5.4 км и Bahrain Outer Circuit 3.5 км) обязаны оставаться
   разными записями `tracks` — разница на километры далеко за порогом
   допуска.

### 4.5 Идемпотентность импорта

1. Идемпотентность по **SHA-256 хэшу сырого содержимого файла**
   (`file_hash`, `UNIQUE`) — повторная загрузка того же файла обязана
   определяться как дубликат и не создавать вторую сессию.
2. Дубликатом считается только запись со статусом **не `failed`** — файл,
   чей прошлый импорт провалился (временный сбой БД, диска и т.п.), обязан
   допускать повторную попытку, не блокируясь навечно занятым `UNIQUE`
   значением хэша.
3. Повтор после `failed` обязан переиспользовать ту же строку `import_jobs`
   (тот же `id`), а не вставлять вторую с тем же хэшем.

### 4.6 Валидация и DLQ

1. Валидация круга — двухступенчатая: сначала структурная (Zod-схема:
   допустимые диапазоны времени круга — от 10 секунд до 24 часов,
   секторов — до 12 часов), затем семантическая (сумма трёх секторов не
   должна отличаться от времени круга больше чем на 5%; дата сессии не
   может быть в будущем).
2. Невалидные круги обязаны попадать в `import_errors` (DLQ) с кодом
   ошибки (`VALIDATION_ERROR`/`PARSE_ERROR`/`SEMANTIC_ERROR`) и не прерывать
   импорт остальных валидных записей.
3. Импорт файла в целом обязан провалиться, если доля валидных кругов
   (среди некруговых-по-питу записей) ниже `VALID_LAP_THRESHOLD_PCT` (80%).
4. Файл без единого участника (`0 <Driver>` в детектированной секции
   сессии) ИЛИ без единого круга обязан считаться **пропуском**
   (`status=skipped`, код `ZERO_LAPS`), не ошибкой — семантически валидный
   лог (например, все отключились до записи хотя бы одного участника).

### 4.7 Дедупликация сессий при реконнекте (`server/sessionSupersede.ts`)

1. При разрыве соединения выделенный сервер LMU пишет **новый** файл лога
   вместо дополнения старого; устойчивого идентификатора сессии (SessionID/
   GUID) в формате нет.
2. «Это тот же самый забег» определяется по совпадению: `event`
   (`TrackEvent`) + точный `sessionType` + `trackId` + пересечение состава
   пилотов (коэффициент перекрытия ростеров ≥ `ROSTER_OVERLAP_THRESHOLD`
   = 0.5, считается как доля меньшего ростера, встретившаяся в обоих) — в
   пределах временного окна `SUPERSEDE_MAX_GAP_MS` = ±24 часа от даты нового
   файла (реконнект — минуты/часы; одноимённое регулярное событие турнира
   неделей позже — дни/недели, не должно ложно склеиваться).
3. Если найдено два кандидата с одинаковым (в пределах машинной точности)
   overlap — предпочтение отдаётся **безопасному варианту**: импортировать
   как новую сессию, а не гадать, какую из существующих заменять.
4. Из двух дампов «полнее» считается тот, у кого больше суммарное число
   распарсенных кругов; равенство — не повод заменять (SKIP).
5. При замене (`REPLACE`): все данные заменяемой сессии (`sessionResults`,
   `sessionLaps`, `lapTimes`, `sessionIncidents`, `sessionSectorBests`,
   `sessionTrackLimits`, сама строка `sessions`) удаляются в **той же
   транзакции**, что и вставка новой сессии; `import_jobs` заменённого
   импорта не трогается (остаётся информационной записью с «мёртвым»
   `session_id`, ни на что не влияет).
6. Живая телеметрия уже пройденных кругов (топ-спид, топливо, износ шин —
   **не** время круга/секторов, они идентичны между дампами) переносится
   из заменяемого дампа в новый, если новый дамп её обнулил — реконнект
   сбрасывает локальное физическое состояние пилота, и сервер переписывает
   уже пройденные круги «с нуля» (полный бак, 0% износа, топ-спид 0).
7. В журнале импорта на клиенте замена обязана отображаться отдельным
   уровнем «предупреждение» (амбер), отличимым от обычного «ok».
8. **[ОГРАНИЧЕНИЕ]** Сессии практики/квалификации, импортированные до
   исправления бага чтения `Minutes`/`Laps` (см. §4.1 п.3), остались с
   `session_duration_min = NULL` и не пересчитываются задним числом —
   единственный способ поправить исторические данные — полная очистка БД
   и повторная загрузка тех же файлов.

### 4.8 Пакетная обработка

1. Batch insert больших наборов (`session_laps`, `lap_times`, `import_errors`)
   обязан идти чанками по `CHUNK_SIZE` = 500 записей внутри одной транзакции
   — не построчными вставками и не единым INSERT без ограничения размера.
2. Поиск/создание пилотов сессии обязан идти одним batched-запросом на всех
   участников сразу (1 SELECT по всем именам + по 1 INSERT на реально
   нового пилота), не отдельным `SELECT * FROM drivers` на каждого пилота
   каждого импортируемого файла (полное сканирование таблицы на каждый вызов).
3. Поиск трассы обязан фильтроваться по каноничному имени на уровне SQL
   (`WHERE lower(name) = ...`), не полным сканированием таблицы `tracks`
   с фильтрацией в JS.

## 5. Требования к телеметрии

### 5.1 Формат `.duckdb`-файла

Файл записи телеметрии LMU содержит:
- `metadata` — key/value о заезде (пилот, трасса, сетап, погода).
- `channelsList` (channelName, frequency Гц, unit) — непрерывные каналы,
  каждый в одноимённой таблице (`value` либо `value1..value4`), без
  явного `ts`.
- `eventsList` (eventName, unit) — событийные каналы (например, `Lap`),
  таблицы с колонками `ts, value[1..4]`, запись только при изменении.

### 5.2 Импорт (потоковое чтение)

1. Файл обязан открываться через `@duckdb/node-api` в режиме **read-only**.
2. Каналы и события читаются **потоково** (`conn.stream()` +
   `yieldRowObjectJs()`), партиями по `CHUNK_SIZE`, а не через
   `runAndReadAll()` — материализация всей записи (до нескольких миллионов
   сэмплов) в памяти Node недопустима: на продовой VM с ограниченным
   V8-heap это приводило к `JavaScript heap out of memory` и падению всего
   процесса (проверено на реальном файле 98 каналов / 2 637 082 сэмпла:
   импорт держит память ~130 МБ вместо OOM).
3. Каждая партия немедленно пишется в `telemetry_samples` батчами внутри
   одной транзакции — пиковая память процесса не должна зависеть от размера
   файла/числа сэмплов.
4. `ts` для канальных (не событийных) сэмплов в исходном файле отсутствует —
   восстанавливается как `recordingBaseTs + seq / frequencyHz`, где
   `recordingBaseTs` — минимальный первый `ts` среди всех событийных таблиц
   файла (единая временная шкала обязательна для сопоставления каналов
   с границами кругов из события `Lap`).
5. Идемпотентность — по SHA-256 хэшу **сырых байт** файла (`telemetry_
   import_jobs.file_hash`, `UNIQUE`), тот же принцип «не блокировать повтор
   после failed», что и в §4.5.
6. Максимальный размер загружаемого файла — 150 МБ (ограничение на
   мидлварь `express.raw()`, применяется только к этому роуту, не к
   глобальному `express.json()`).

### 5.3 Чтение телеметрии

1. Границы кругов (`getSessionLaps`) — по событию `Lap` (новая строка при
   смене номера круга); конец последнего круга — конец записи
   (`MAX(ts)`), посчитанный SQL-агрегатом на стороне Postgres, а не
   выгрузкой всех `ts` сессии в Node для поиска максимума вручную (это
   раньше приводило к `499`/`502` на больших сессиях).
2. График/карта одного круга (`getLapSeries`) — GPS lat/lon, дистанция
   круга, педали, скорость выравниваются на единую временную сетку:
   базовая сетка — канал с **максимальной частотой** среди используемых
   (обычно скорость, 100 Гц), остальные каналы подтягиваются **линейной
   интерполяцией** между двумя ближайшими реальными сэмплами по `ts` (не
   ступенчатым копированием ближайшего значения, не простым
   downsampling'ом самого частого канала до частоты GPS).
3. За пределами диапазона данных канала — берётся крайнее известное
   значение (без экстраполяции).
4. Если у сессии нет каналов GPS-широты/долготы — карта отдаёт пустой
   набор точек, не ошибку.

## 6. Требования к REST API

Формат ошибок — `{ message, details? }`, коды: `400` (невалидный ввод),
`401`/`503` (admin-эндпоинты), `404` (не найдено), `409` (дубликат
файла/уже импортирован), `500` (внутренняя ошибка, с текстом причины,
включая `error.cause` от Postgres — не просто общее «Failed query»).

### 6.1 Справочники и заезды

| Метод | Путь | Требование |
|---|---|---|
| GET | `/api/tracks` | список всех трасс |
| GET | `/api/tracks/:id` | `:id` — положительное целое (Zod), иначе `400`; `404` если не найдена |
| GET | `/api/drivers` | без явного `limit` — до 5000 записей (не молчаливая обрезка до 500, список пилотов растёт медленнее кругов) |
| GET | `/api/drivers/:id` | как выше |
| GET | `/api/drivers/:id/incidents` | инциденты + нарушения трек-лимитов пилота, только по гоночным сессиям, роль (`caused`/`received`) относительно запрошенного пилота |
| GET | `/api/laps` | фильтры `trackId`/`driverId`/`carClass`/`conditions`/`sessionId`/`sessionCourse`; **без фильтра и без явного `limit`** — лимит по умолчанию 500 (эндпоинт никогда не отдаёт весь `lap_times` безусловно); с любым фильтром — лимит применяется, только если запрошен явно (в пределах `maxLimit` 5000) |
| GET | `/api/laps/best` | личный лучший круг каждого пилота на каждой трассе+класс+course — заменяет паттерн «выгрузить все круги и свернуть на клиенте»; размер ответа ограничен числом комбинаций трасса×класс×пилот, отдельной пагинации не требует |
| GET | `/api/sessions` | без явного `limit` — до 5000 (не молчаливая обрезка до 500 без пагинации и без индикации усечения) |
| GET | `/api/sessions/:id` | `404` если не найдена |
| GET | `/api/sessions/:id/laps` | обогащённые круги (`driverName`/`carNumber`/`isPlayer`/секунды) одним JOIN-запросом, не тремя запросами со склейкой через JS `Map` |

### 6.2 Телеметрия (чтение)

| Метод | Путь | Требование |
|---|---|---|
| GET | `/api/telemetry/sessions` | список записей |
| GET | `/api/telemetry/sessions/:id` | метаданные + реестр каналов; `404` если нет |
| GET | `/api/telemetry/sessions/:id/laps` | границы кругов |
| GET | `/api/telemetry/sessions/:id/laps/:lapNumber/series` | `:lapNumber` — неотрицательное целое (у телеметрии круг может быть `0` — формационный/выездной), не PK-схема; `404` если круг не найден |

### 6.3 Импорт логов

| Метод | Путь | Требование |
|---|---|---|
| POST | `/api/import` | тело — `{ files: [{ fileName, content }] }`; синхронная обработка каждого файла по очереди в рамках одного HTTP-запроса (транзакции на файл ~5000 строк укладываются в < 500 мс — асинхронная очередь не нужна); пустой файл — `skipped`, не ошибка; ответ — сводка `{ imported, skipped, totalLaps, total, results[] }`, HTTP `200`, если есть хотя бы один успех **или** все неуспехи — только пропуски, иначе `400` |
| DELETE | `/api/import/all` | требует admin-токен; полная очистка всех импортированных данных (заезды, сессии, пилоты, трассы, задачи импорта, DLQ) одной транзакцией, в порядке, уважающем зависимости (сначала листовые таблицы) |
| GET | `/api/import/:id/status` | статус задачи по `id` |
| GET | `/api/import/:id/errors` | содержимое DLQ задачи; `404` если задачи нет |

### 6.4 Импорт телеметрии

| Метод | Путь | Требование |
|---|---|---|
| POST | `/api/import/telemetry?fileName=<name>` | тело — сырые байты (`application/octet-stream`), лимит 150 МБ; ответ — `{ ok, fileName, importId, telemetrySessionId, channelCount, sampleCount }` |
| DELETE | `/api/import/telemetry/all` | требует admin-токен; очищает только таблицы телеметрии, не трогает `sessions`/`lap_times` |

### 6.5 Admin-защита

1. `requireAdminToken` защищает деструктивные роуты (`DELETE /api/import/all`,
   `DELETE /api/import/telemetry/all`) заголовком `Authorization: Bearer
   <ADMIN_TOKEN>`.
2. Если `ADMIN_TOKEN` не задан на сервере — роут обязан отвечать `503`, **не**
   пропускать запрос без проверки (забытая настройка не должна молча
   открывать деструктивный эндпоинт всем).
3. Сравнение токена — за постоянное время (`timingSafeEqual`), не
   `===`/`indexOf` — исключает восстановление токена по задержке ответа.
4. Клиент при первом использовании кнопки очистки один раз запрашивает
   токен и запоминает его в браузере.

### 6.6 Special Events

| Метод | Путь | Требование |
|---|---|---|
| GET | `/api/special-events` | кэш в памяти: TTL 6 часов при успешном скрейпе, TTL 5 минут при ошибке (быстрое восстановление после сбоя источника); ответ содержит `source: "live" \| "static"`, чтобы UI мог отличить свежие данные от замороженного фолбэка |
| POST | `/api/special-events/refresh` | сбрасывает кэш и повторяет скрейп немедленно |

### 6.7 Валидация query/path-параметров

Все числовые `:id`/`:lapNumber` из пути и query-параметры списочных
эндпоинтов (`trackId`, `driverId`, `limit`, `offset` и т.д.) обязаны
проверяться Zod-схемами **до** похода в БД. Невалидный ввод (например,
нечисловой `trackId`) обязан возвращать `400` с описанием ошибки — не
превращаться молча в `NaN` внутри SQL-фильтра.

## 7. Требования к модели данных

15 таблиц PostgreSQL, единый источник схемы — `shared/schema.ts` (Drizzle +
drizzle-zod). Полное описание колонок — `docs/database-schema.md`. Ключевые
инвариантные требования:

1. Внешние ключи — **логическая** связь по соглашению именования (`*_id`),
   не физическое ограничение Postgres (`.references()` не используется) —
   целостность поддерживается приложением, не СУБД.
2. `session_laps` дублирует `session_id`/`driver_id` (денормализация поверх
   `session_result_id`) — обязательно для упрощения аналитических запросов
   без лишних JOIN.
3. `import_jobs.session_id`/`telemetry_import_jobs.telemetry_session_id` —
   заполняются **после** того, как основная запись создана внутри той же
   транзакции; остаются `NULL` при `status = "failed"`.
4. `telemetry_samples` — EAV-таблица (`channel_id`, `seq`, `ts`,
   `value1..value4`) вместо отдельной Postgres-таблицы на каждый канал, как
   в исходном `.duckdb` — самая крупная таблица в БД (до нескольких
   миллионов строк на одну запись), обязан быть индекс по `channel_id`.
   Запросы к ней обязаны быть ограничены по `ts` или сведены к SQL-агрегатам
   — полное чтение таблицы в Node недопустимо (см. §5.3).
5. `sessions.has_co_drivers`, `session_results.stint_start_lap/stint_end_lap/
   stint_start_sec/stint_end_sec` — nullable-колонки, добавленные
   аддитивно (без потери существующих данных).
6. Обогащённые API-типы (`SessionEnriched`, `SessionFull`, `LapTimeEnriched`,
   `SessionLapEnriched`, `DriverIncidentsResponse`, `SessionIncidentEnriched`)
   — контракт между сервером и клиентом, должны оставаться синхронными со
   схемой таблиц (проверяется TypeScript-компиляцией, не только рантаймом).

## 8. Нефункциональные требования

### 8.1 Производительность и память

1. Импорт `.duckdb`-файла произвольного размера (до 150 МБ, потенциально
   миллионы сэмплов) обязан держать пиковую память процесса Node
   ограниченной константой, не пропорциональной размеру файла — потоковое
   чтение обязательно (см. §5.2).
2. Списочные эндпоинты без явного `limit` обязаны иметь разумный дефолт
   (500–5000 в зависимости от эндпоинта), чтобы не отдавать весь датасет
   безусловно; при этом осознанный запрос большей страницы (в пределах
   `maxLimit`) не должен блокироваться.
3. Агрегаты по крупным таблицам (`MAX(ts)` для границ записи телеметрии,
   пагинация лидербордов и т.п.) обязаны вычисляться SQL-агрегатами на
   стороне Postgres, не построчным чтением в Node.
4. Поиск/создание справочных сущностей при импорте (трассы, пилоты)
   обязан избегать полного сканирования таблицы на каждый вызов —
   batched-запросы по всем именам сразу.

### 8.2 Безопасность

1. Деструктивные операции (полная очистка БД/телеметрии) обязаны требовать
   admin-токен, сравниваемый за постоянное время; отсутствие настроенного
   токена — жёсткий отказ (`503`), не пропуск проверки.
2. Все внешние числовые входы API (path/query-параметры) обязаны проходить
   структурную валидацию Zod до использования в SQL-запросах.
3. Импортируемые XML/`.duckdb`-файлы обрабатываются read-only парсерами;
   структурная и семантическая валидация данных лога обязательна до записи
   в БД (см. §4.6).

### 8.3 Надёжность/идемпотентность

1. Повторная загрузка одного и того же файла (лог или телеметрия) не
   должна создавать дублирующие записи — гарантия через `UNIQUE` хэш
   содержимого + проверка статуса перед вставкой.
2. Реконнект LMU (новый файл лога вместо продолжения старого) не должен
   приводить к задвоению сессии в БД — обязательна логика supersede
   (см. §4.7).
3. Все многошаговые операции записи (импорт файла, supersede, полная
   очистка) обязаны выполняться в транзакции БД — частичная запись при
   сбое посреди операции недопустима.
4. Фоновый импорт (авто-скан папки, обработка очереди файлов) не должен
   прерываться при переходе пользователя на другую страницу приложения —
   состояние живёт в провайдере уровня приложения, не в компоненте страницы.

### 8.4 Локализация

Полная поддержка RU/EN для всех пользовательских текстов, включая числовые
склонения для русского языка и форматирование дат/времени с учётом локали.
Несоответствие ключей между словарями RU/EN обязано ловиться на этапе
компиляции TypeScript, не в рантайме.

### 8.5 Доступность и адаптивность

1. Различение состояний (медали, уровни журнала импорта, игрок/ИИ) не
   должно полагаться **только** на цвет — обязательно дублирование иконкой/
   текстом (важно для дальтоников и беглого просмотра).
2. Все интерактивные строки таблиц обязаны быть доступны с клавиатуры, не
   только мышью.
3. Ключевые таблицы и layout-блоки обязаны корректно работать на ширине
   от 390px без потери данных и наложения текста.

### 8.6 Качество кода и тестируемость

1. ESLint (flat config, `typescript-eslint` + `eslint-plugin-react`/
   `react-hooks`) и Prettier обязаны проходить в CI на каждый push/PR
   (`.github/workflows/lint.yml`) — отдельные джобы для линта и форматирования.
2. Модульные тесты (Vitest) обязательны как минимум для: парсера логов,
   нормализатора, валидаторов, воркера импорта (включая идемпотентность),
   дедупликации сессий (`sessionSupersede`), слоя хранения (`storage`),
   REST-роутов, парсера Events, схемы БД, форматирования времени,
   селекторов Session Detail.
3. Инсерт-массивы импорт-воркера обязаны быть типизированы через сгенерированные
   из схемы типы (`InsertLapTime`, `InsertSessionLap`, `InsertImportError`),
   не `any[]` — рассинхрон со схемой Drizzle обязан ловиться при компиляции,
   не в рантайме на пути импорта.
4. TypeScript-проверка типов (`npm run check`) обязана проходить без ошибок.

## 9. Требования к инфраструктуре и деплою

1. Продакшн-сборка — многоступенчатый Docker-образ (`node:20-alpine`):
   стадия сборки (`npm run build`), стадия рантайма с `libstdc++`/`libgcc`
   для нативного биндинга DuckDB.
2. `docker-compose.yml` поднимает PostgreSQL + приложение, порт хоста 3000 →
   контейнер 5000.
3. Схема БД применяется через `drizzle-kit push` (без versioned-миграций).
   Деплой-пайплайн (`.github/workflows/deploy.yml`) обязан прогонять
   `docker compose run --rm dashboard npx drizzle-kit push --force`
   **до** пересоздания контейнера с новым образом — иначе есть окно, где
   новый код обращается к ещё не существующим в БД колонкам и падает с
   `500` на первом же запросе (задокументированный инцидент —
   `has_co_drivers`/`stint_*` после мержа командных гонок).
4. Обязательные переменные окружения: `DATABASE_URL` (подключение к
   Postgres), `ADMIN_TOKEN` (защита деструктивных операций, без него —
   `503` на этих роутах, не открытый доступ).
5. CI (`lint.yml`, `docs-lint.yml`, `update-lockfile.yml`, `deploy.yml`)
   обязан блокировать мерж/деплой при незелёном линте/форматировании;
   `docs-lint` (markdownlint) — с проектным конфигом
   (`.markdownlint.jsonc`), отключающим правила, конфликтующие с принятым
   стилем документации (`MD013` лимит длины строки, `MD024` дубли
   заголовков в CHANGELOG).

## 10. Известные ограничения и принятые компромиссы

Эти пункты — не дефекты для исправления «на автомате», а зафиксированные
осознанные решения; учитывать при дальнейшем изменении требований.

1. Нет внешних ключей на уровне СУБД — целостность связей полностью на
   совести приложения.
2. Нет versioned-миграций БД — только `drizzle-kit push` по live-схеме;
   откат схемы к прошлой версии не поддерживается.
3. Единственная admin-роль на общем токене — нет индивидуальных учётных
   записей, ролей или журнала действий администратора.
4. Daily Races — статические данные в коде, требуют ручного обновления;
   API-источника у LMU нет.
5. Special Events скрейпятся regex-парсингом HTML внешнего сайта — хрупко
   к изменению вёрстки источника (фолбэк на статику предусмотрен и
   логируется, но не является полноценной заменой живых данных).
6. Спутниковая калибровка карты трассы (`trackMapCalibration.ts`) реализована
   только для одной трассы (Spa-Francorchamps); остальные используют
   схематичный SVG.
7. Исторические сессии практики/квалификации с багом `session_duration_min
   = NULL` не пересчитываются автоматически — требуется ручная переимпорт
   после полной очистки БД.
8. Определение страны пилота по имени (`guessCountry()`) — эвристика по
   спискам характерных фамилий/суффиксов, не полноценная база данных
   национальностей; ожидаемо даёт `"—"` для нераспознанных случаев.

## 11. Детальная UI-спецификация: дизайн-система, типографика, таблицы

Раздел фиксирует конкретные визуальные требования — какие таблицы
отрисовываются, из каких колонок состоят, как выровнены данные, какие шрифты
и цвета используются — реконструировано напрямую из Tailwind-классов
компонентов. Все таблицы приложения — это либо семантический HTML `<table>`,
либо CSS `grid`/`flex`-раскладка со строгой ролевой разметкой
(`role="table"`/`role="row"`/`role="cell"`); универсальный shadcn-компонент
`client/src/components/ui/table.tsx` **не используется нигде** — каждая
таблица свёрстана вручную под конкретный набор колонок.

### 11.1 Дизайн-токены

1. Тема переключается классом `.dark` на `<html>`; все цвета заданы как
   HSL-переменные (`--primary`, `--background`, `--card`, `--muted`,
   `--chart-1..5` и т.д.) и потребляются через Tailwind-алиасы
   (`bg-primary`, `text-muted-foreground`, …) — обязательное правило: новый
   UI-код не должен захардкоживать HEX/RGB, только токены темы (кроме
   специальных семантических цветов состояния, см. п.3).
2. Ключевые значения токенов:

   | Токен | Светлая тема | Тёмная тема | Назначение |
   |---|---|---|---|
   | `--background` | `0 0% 100%` (белый) | `220 15% 7%` (почти чёрный, с синим подтоном) | фон страницы |
   | `--foreground` | `0 0% 9%` | `0 0% 96%` | основной текст |
   | `--card` | `0 0% 98%` | `220 13% 10%` | фон карточек/таблиц |
   | `--border` | `0 0% 91%` | `220 10% 16%` | границы, разделители строк |
   | `--primary` | `8 88% 52%` (красно-оранжевый, гоночный акцент) | `8 92% 56%` | акцентный цвет (логотип, активная вкладка, CTA-кнопки, активная сегментированная кнопка «Все») |
   | `--muted-foreground` | `0 0% 40%` | `220 8% 62%` | второстепенный текст, подписи колонок |
   | `--chart-1..5` | 8°/38°/172°/199°/262° (hue), ~50-60% lightness | те же hue, ярче на 4-8% | графики Recharts + фолбэк-цвета классов машин |
   | `--radius` | `0.5rem` | — | базовый радиус скругления (карточки — `rounded-xl`, кнопки/бейджи — `rounded-md`) |

3. Специальные семантические цвета (заданы напрямую Tailwind-палитрой, не
   через CSS-переменные темы — одинаковы в обеих темах, т.к. несут
   фиксированный смысл):
   - **Зелёный** (`green-400/500`) — реальный игрок (`DriverName`), личный
     лучший сектор/круг, положительная метрика (`StatTile variant="green"`).
   - **Жёлтый/амбер** (`amber-400`, `yellow-400/500/600`) — ИИ-пилот
     (`DriverName`), квалификация (`SESSION_TYPE_BADGE.qualify`),
     предупреждение в журнале импорта, средний компаунд шин (`M`).
   - **Красный** (`red-400/500/600`) — тип сессии «Гонка», худшая метрика
     (`StatTile variant="red"`), мягкий компаунд шин (`S`), деструктивные
     действия (кнопка очистки БД).
   - **Синий** (`blue-400/500`) — тип сессии «Тренировка».
   - **Фиолетовый** (`purple-500`) — абсолютный лучший сектор/круг **среди
     всех** участников сессии (приоритетнее личного зелёного рекорда).
   - **Золото/серебро/бронза** (`text-yellow-400` / `text-slate-400` /
     `text-amber-700`) — медали позиций 1/2/3 (`getMedalColorClass()`),
     единственное место, где для медалей 1/2/3 используются три разных цвета
     (раньше все три места красились одинаково — исправленный баг).
   - Классы машин — фиксированная палитра на базе `--chart-1..6`:
     Hypercar/Hyper → chart-1 (красно-оранжевый), LMP2 → chart-4 (голубой),
     LMP3 → chart-5 (фиолетовый), GTE → chart-3 (бирюзовый), GT3 → chart-2
     (жёлто-оранжевый), GT4 → chart-6. Неизвестный класс — нейтральный
     `bg-muted/40 text-muted-foreground`.
4. Скругления: `--radius-lg` = 9px (карточки, кнопки), `--radius-md` = 6px
   (инпуты, мелкие бейджи-круги компаунда шин), `--radius-sm` = 3px.
5. Интерактивная «elevate»-система (`.hover-elevate`/`.active-elevate-2`,
   `client/src/index.css`): при наведении/клике элемент получает
   полупрозрачную наложенную подсветку (`--elevate-1` = 3-4% белого/чёрного,
   `--elevate-2` = 8-9%) вместо смены фонового цвета через отдельный класс —
   единый механизм hover/active для карточек, кнопок и строк.
6. Скроллбар тематизирован во всём приложении: 10px, цвет большого пальца —
   `hsl(var(--border))`, при наведении — `hsl(var(--muted-foreground))`;
   для Firefox — `scrollbar-width: thin` с теми же цветами. Не системный
   белый скроллбар браузера.

### 11.2 Шрифты и типографика

Три шрифтовых семейства, подключены как CSS-переменные и Tailwind-утилиты:

| Класс | Шрифт | Где используется |
|---|---|---|
| `font-sans` (по умолчанию, `body`) | Inter, sans-serif | весь обычный текст: подписи, названия команд/машин, описания |
| `.font-display` | Oxanium → Inter (фолбэк) | заголовки страниц (`<h1>`), названия трасс/сессий в шапках карточек — гоночный «дисплейный» шрифт с угловатыми формами букв |
| `.font-data` (+ `.tabular-nums`) | JetBrains Mono → monospace | **все числовые данные**: время круга/сектора, позиции, счётчики, даты в компактном виде — моноширинный шрифт с `font-variant-numeric: tabular-nums lining-nums`, чтобы цифры не «прыгали» по ширине при обновлении значений в таблице |

Правило дизайн-системы: **любое числовое/временное значение в таблице
обязано использовать `font-data` + `tabular-nums`**, обычный текст (имена,
названия, статусы) — обычный `font-sans`. Это разделение выдержано во всех
без исключения таблицах приложения (см. §11.4).

Типографическая шкала (по фактическим классам):

| Класс | Размер | Где |
|---|---|---|
| `text-[10px]` | 10px | подписи `StatTile` (`uppercase tracking-wider`), доли секунды в мини-плитках, буквенные лейблы шин FL/FR/RL/RR |
| `text-[11px]` | 11px | заголовки колонок таблиц (`uppercase tracking-wider text-muted-foreground`), мелкие бейджи классов в таблице сессий |
| `text-xs` | 12px | тело большинства таблиц (`SessionResultsTable`, `Leaderboards`, `DriverLapTable` заголовки), бейджи |
| `text-sm` | 14px | основной текст таблиц/карточек, значения `StatTile` без варианта |
| `text-base` | 16px | подзаголовки, название трассы в `SessionInfoCard` рядом с бейджем |
| `text-lg` | 18px | заголовки блоков (`h2` секций Card) |
| `text-xl` | 20px | заголовки страниц (`<h1 className="font-display text-xl font-bold tracking-tight">`) |
| `text-2xl` | 24px | крупные счётчики (`ActivityTile` количество сессий) |
| `text-4xl`/`text-5xl` (`sm:`) | 36px/48px | герой-показатель «Лучший круг сезона» на Overview — самое крупное числовое значение во всём приложении |

Насыщенность: `font-semibold`/`font-bold` — заголовки, лучшие/выделенные
значения (личный/абсолютный рекорд, победитель); `font-medium` — имена
пилотов и активные интерактивные элементы; обычный вес — второстепенные
данные (команда, авто, дата). Подписи колонок и мини-лейблы почти везде
идут в `uppercase` + `tracking-wider` + `text-muted-foreground` — это
единый визуальный маркер «это подпись, не данные» по всему приложению.

#### 11.4.9 Профиль пилота — три таблицы + список сессий

1. **Личные рекорды по трассам** (`<table>`): Трасса+конфигурация (left,
   иконка `MapPin`) → Класс (`Badge`) → Круг (right, `font-data
   tabular-nums`, `font-bold text-primary` если это личный рекорд равен
   абсолютному) → Отставание от рекорда (right, `formatDelta()` либо бейдж
   «Рекорд трассы» если сам держит) → Дата (right, скрыта `< sm`).
2. **История сессий** — не `<table>`, а `flex`-строки с фиксированными
   `w-[Npx] shrink-0` колонками (мин. ширина строки 760px, горизонтальный
   скролл на мобильном): Тип (`SessionTypeBadge`, 110px) → Дата (130px) →
   Трасса + при наличии диапазон стинта строкой ниже (`flex-1 min-w-0`) →
   Класс (`Badge`, 70px) → Позиция в классе (70px, right, медаль топ-3) →
   Лучший круг (90px, right, скрыт `< md`) → Статус (70px, right, скрыт
   `< lg`) → шеврон.
3. **Инциденты** (`<table>`): Дата → Трасса → Роль (`Badge` красный
   «Виновник» / синий «Пострадавший») → Второй участник → Тяжесть (right,
   `font-data tabular-nums`, + бейдж «Неподвижный объект» при ударе о
   стену/бортик).
4. **Нарушения трек-лимитов** (`<table>`): Дата → Трасса → Круг (right) →
   Очки (right, `текущие / предел`) → Решение (скрыто `< sm`).
5. Шапка профиля: имя (`DriverName`, `font-display text-xl font-bold`) +
   бейдж «Игрок»/«ИИ» (зелёный/амбер) + бейдж «Игрок c года X»; ниже —
   команда/страна. KPI-плитки (6 шт., `grid-cols-[repeat(auto-fill,
   minmax(140px,1fr))]`): Лучший круг, Сессий, Кругов, Побед, Подиумов,
   Средняя позиция — каждая своя `Card` с иконкой `text-[13px]`, подписью
   `uppercase tracking-widest text-muted-foreground` и значением
   `font-data text-lg font-bold tabular-nums`.

#### 11.4.10 Telemetry Detail — пикер круга

Не таблица, а горизонтальный ряд кнопок (`role="tablist"`) в
`bg-muted/40`: активный круг — `bg-primary text-primary-foreground shadow`,
неактивный — `text-muted-foreground`. Каждая кнопка — номер круга (с 1) +
длительность (`formatLap()`, `font-data text-[10px] tabular-nums
opacity-80`) в две строки.

#### 11.4.11 Import — журнал импорта

Не таблица, а вертикальный список записей (`<ul>`), каждая строка —
иконка уровня + время (`toLocaleTimeString()`, `font-data
text-muted-foreground`) + текст сообщения, цвет текста зависит от уровня
(`ok` изумрудный / `error` красный / `skip` жёлтый / `warn` амбер / `info`
нейтральный) — см. §11.1 п.3 для цветовой семантики уровней. Счётчики
импорта — 5 плиток `StatCard` (обнаружено/в очереди/импортировано/
пропущено/ошибок), значение `font-data text-xl font-bold tabular-nums`.

### 11.5 Сквозные UI-правила (применимы ко всем таблицам)

1. **Выравнивание**: текстовые/именные колонки — всегда `text-left`;
   числовые, временные и связанные с ними производные (отставание,
   интервал, дата в компактном виде) — всегда `text-right`; иконки/бейджи
   без чёткого смысла направления (класс машины, статус, компаунд шин) —
   `text-left` либо `text-center`, если бейдж круглый/квадратный
   фиксированного размера (позиция, компаунд шин).
2. **Числа = `font-data` + `tabular-nums`** без исключений — гарантирует,
   что колонки времени/позиций не «прыгают» по ширине между строками.
3. **Иерархия цвета результата**: фиолетовый (абсолютный лучший
   среди всех) > зелёный (личный лучший) > обычный текст. Красный
   зарезервирован за «худшим» показателем и семантикой гонки/деструктивных
   действий, никогда не за обычным нейтральным значением.
4. **Адаптивное сокрытие колонок**, а не сокращение текста: второстепенные
   колонки (команда, авто, дата, отставание, сектора) скрываются целиком на
   узких экранах (`hidden ... sm/md/lg:table-cell`) — данные остаются
   доступными через возврат к более широкому экрану или горизонтальный
   скролл контейнера, не обрезаются потерей информации без возможности
   восстановить её иначе, чем resize окна.
5. **Строки-ссылки вместо кнопок**: там, где строка ведёт на деталь
   (Sessions, история сессий пилота, недавние сессии на Overview), вся
   строка — интерактивный `<Link>`/`<a>`, а не отдельная кнопка/иконка
   внутри строки — с `hover:bg-muted/40`, курсором `pointer` и видимым
   `focus-visible:ring-2 focus-visible:ring-primary` для навигации с
   клавиатуры.
6. **Разделители строк** — `border-b border-border/60` (не полноценный
   `border-border` — более мягкий, полупрозрачный разделитель внутри
   таблиц), последняя строка — `last:border-0` (без нижней границы).
7. **Заголовки колонок** — единый паттерн по всему приложению:
   `text-[11px]`/`text-xs` + `uppercase` + `tracking-wider` +
   `text-muted-foreground`, без исключений, независимо от того, `<table>`
   это или CSS grid/flex.
